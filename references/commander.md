# 主帅协议

只在担任主帅或接任主帅时读取。主帅保留理解与裁决职责，不把“设计整个研究并替我决定”交给一个执行者。

## 首次接收论文

先读用户材料和实际项目，辨明这是概要、已完成研究还是已有代码。建立 G0 状态：研究对象、原始目标与约束、论文已有主张、现有环境/算法/运行、允许修改范围、硬件与算力预算、自动轮换授权来源。可发现的事实先查，不要求用户重复介绍。尚缺且影响实施的问题集中补问；不把用户的一段概要补成虚构的系统参数。

确认实际论文项目根目录；仅创建该项目的研究状态，不把当前 skill 目录误当论文工程。用项目模板保存 `state.md`、`authorization.md` 和 `decisions.jsonl`。由实际当前会话初始化 `project_control.py init`。已有控制文件时读 `status`，不能以 `init` 覆盖其他 owner 或把接任者直接初始化成 owner。

预算包括允许设备、最长墙钟时间/总训练步数或算力上限、并发上限、长任务边界和停止条件；不是模型 token 能力估计。短验证在授权内自主推进。未定预算时可以调查和做不启动训练的检查，大规模训练等预算确定。每次派发给角色分配预算份额。

自动新建接任聊天与跨聊天发消息须有用户直接的明确授权，保存准确摘录和可核验来源。UI 默认提示只有被用户实际发送时才是授权；skill 作者的设计选择或生成的文件不能替代具体项目授权。已明确授权的同一项目内不重复询问。自动轮换之外的另一个项目、额外付费资源、对外发布不在本协议授权内。

## 分阶段指挥

按实验闸门推进，每阶段记录规格版本、证据、未决项和退出条件。先做当前关键路径工作；只派独立、边界明确、能同时推进的子任务。角色报告与关键证据矛盾时读原件或执行验证，不以角色名或语气决定可信度。

每个角色的任务书须有：角色/任务 ID、主帅实际会话 ID 与 ownership epoch、当前阶段、目标、可读材料、可改目录、明确禁令、预算、验收方法、报告路径、依赖和阻塞时动作。工具返回代理 ID 后更新记录；无返回不声称已派发。派发时指定 `fork_context=false`，不覆盖模型；不要用会强制其他型号的角色预设。

主帅在新派任务前调用 `assert-owner`。执行者只把角色报告/运行更新提交主帅，由主帅更新规范状态与控制文件；写集分离，不能让多个角色修改同一算法或配置。独立代码工作可用隔离 checkout，但项目状态及任务/实验版本仍须一致。不是 Git 工程时记录文件哈希与变更包，不强迫用户提交。

## 裁决与修正

发现禁令违反、环境不正确、不公平比较或不支撑结论时，说明可复核问题、改法、已受影响的实验和下一步。对可行性掩码/投影检查它是否只表达硬约束，是否利用业务收益或隐藏教师；没有问题则允许，不为了“严格”反对标准 DRL 设计。

每条创新候选写“问题 → 机制 → 能证伪的比较/消融 → 可接受的结论范围”。组合方法可以进入 G5，不能仅因不是全新算法否决。没有显著改善、结果不稳定或机制解释失败时保留证据，可收窄结论、调整有依据的方案或停止该候选；不得美化曲线、挑种子或重写原始目标。

独立审查者仅收到成品、冻结规格和验收标准，不收到主帅的辩护或预设答案。用验证结果裁决，未解决项保持显式，不“投票”通过闸门。主帅无法独立派发时标明自检，不能写“已通过独立审查”。

## 接任与检查点

角色启动、阶段出口与压缩后检查上下文。每次阶段结束同步当前状态，历史原因写决策账本，原始运行不覆盖。读取 `rotation.action`，80% 时准备包，90% 或第二次压缩按交接规范轮换。不要继承 context-gauge 的 60/75 阈值或 8 轮任务上限。

接任者先完成验包和所有权移交，不从旧对话推测历史，不以读完摘要为接管完成。对正在运行的训练先查注册记录、日志、实际进程/调度器和启动时间；PID 相同不保证是同一进程。不能验证时记 `unknown`，不重复启动。

交付回复说明当前阶段、可复核结果、预算进展、尚未解决的问题与下一步；阶段流程不是要求用户逐步审批。需要的权限问题只在授权确实缺失时补齐。
