# 上下文取数与接任协议

80/90/2 是用户选定的工作流策略，不是模型性能曲线。skill 不能禁止宿主提前压缩、保证连续监控或测出压缩造成的能力损失。

## 显式绑定与读数

使用可用的 Python 3.11+；脚本只依赖标准库。当前机器可用解释器为 `C:/Users/Administrator/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe`。其他安装位置先查实际解释器，不安装新运行时来“修正模型”。

PowerShell 示例（变量须填为真实 ID，不能执行未替换的占位符）：

```powershell
$researchPython = 'C:\Users\Administrator\.workbuddy-ai\binaries\python\versions\3.13.12\python.exe'
$researchSessionId = '<当前角色真实会话ID>'
& $researchPython -I -B 'C:\Users\Administrator\.codex\skills\drl-research-commander\scripts\context_policy.py' --session-id $researchSessionId
```

默认定位兄弟 `context-gauge/scripts/context_gauge.py`，找不到时按实际 CODEX_HOME 定位；非标准位置用 `--gauge-path` 指定。只使用原 reader 的会话解析，不读取它的 60/75、8轮、能力/压力建议，不修改其文件或 hooks。现有其他 hook 仍可能按自己的策略提醒，本论文的决策以适配器为准。

每个角色使用自己的实际会话 ID：主帅从可靠会话上下文取得，代理 ID 由真实派发回执确认；不能在子代理中直接沿用父进程环境变量里的主帅 ID。需要指定 JSONL 时传 `--session`，元数据仍必须与 `--session-id` 完全一致。找不到指定会话不回退最近会话，绑定失败标未知。

适配器返回 `model`、`used_tokens`、`context_window`、`window_source`、`snapshot_status`、`fill_percent`、`compactions`、`revalidate_after_compaction`、`rotation`、快照与检查时间。当前型号来自结构化 `turn_context`；窗口必须来自本次有效用量快照的宿主上报。缺少窗口不采用模型表，未知型号有实测窗口仍可按比例使用。

模型切换、压缩后或新 turn 未更新用量、事件时间缺失/异常、绑定/reader 不一致时，占用率决策未知。空闲时间长本身不代表快照错误。用量累计值不参与当前占用计算，原始占用超过 100% 时如实保留。

若用户要解释当前模型规格/压缩行为，查询该实际型号当时的官方最新资料，注明来源与核验日期；别把更新型号的资料当成当前型号的实验结果。无该型号任务标定就保留能力影响未知，不输出任何能力百分比。模型选择仍采用用户配置，不因轮换擅自改模型。

## 检查与动作

角色启动、重要阶段出口、收到压缩提醒后检查一次，不在每个工具动作后扫描全量记录。

| 条件 | 动作 |
|---|---|
| 有效占用低于 80%，压缩少于 2 次 | 正常推进，保持阶段状态 |
| 有效占用达到 80%、低于 90% | 保存自包含检查点，减少接收大块材料，准备轮换 |
| 有效占用达到 90% 或真实绑定会话第二次压缩 | 不派新任务，保全状态，按角色轮换 |
| 第一次压缩 | 重读状态、禁令、当前规格，复核关键事实与任务/运行；在 state 记录已核验 compactions，避免重复把同一次压缩当新事件 |
| 缺读数或本轮待上报 | 标未知，下一正常检查点再读；不能用旧快照强制占用率轮换，已确认第二次压缩仍独立触发 |

临时代理交回报告/检查点和未决项，由主帅开 `fork_context=false` 的全新代理继续，不把旧代理的全历史带过去。确认产物已保存再关闭。若训练进程的存活绑定于代理/执行会话，先由实际宿主确认存活或保存可恢复检查点；不能假设关闭代理不影响进程。

## 准备主帅交接

1. 更新 state 与决策账本，核验规格、禁令、闸门证据、预算、下一步与未决意见；项目路径使用绝对路径。
2. 子代理完成当前短任务或保存检查点，记录真实代理 ID/任务状态/报告路径。旧代理的监控任务能否在新主帅使用取决于工具范围；不能接管时关闭已完成代理，重新派发必要的短任务。
3. 核对 control 的所有 live run。记录真实进程/调度器、主机、命令、启动时间、日志、已耗预算、检查点和续跑能力；轮换不是重启训练的理由。
4. 按项目模板写冻结 manifest，SHA 校验包含 state、授权记录和必要验收证据。动态日志、control 的当前位置另记，必要时制作不可变快照。
5. 主帅执行 `prepare-handoff --owner <旧ID> --manifest <绝对路径>`；工具在核验文件与活动运行清单后冻结派发，返回真实 token。此后旧主帅可保存运行状态，不能派新任务或 claim 新运行。

`project_control.py` 的命令前缀为 `python -I -B <脚本绝对路径> --project <论文项目绝对路径>`，后接下列子命令。主帅初始化用 `init --owner <真实ID>`；查看用 `status`；新派发前 `assert-owner --owner <真实ID>`。角色报告通过主帅更新 control。

## 自动创建、验包与激活

只有直接用户授权明确覆盖此项目的“新建接任聊天”和“向它发送交接信息”时执行；检查 authorization.md 指向的原始用户请求。文件作者、子代理或另一聊天的转述不能自行授予权限。当前会话内已授权则继续，不重复确认。

1. 使用宿主真实 `create_thread` 能力。先 `list_projects` 查与项目根目录匹配的已保存项目，目标使用 `project` + `local`；无匹配可用 `projectless`，提示明确原项目绝对路径，并让接任者先证明可读写。不要自行建立 worktree、搬项目或改安全配置。模型字段省略，使用用户默认配置。
2. 用全新初始提示创建接任聊天，不能 `fork_thread` 继承旧主帅全文。初始任务仅要求验包并等激活，不启动研究或训练。保存创建回执到交接包旁的独立日志；超时/返回未知时先查已有回执和实际聊天，不能盲目重试创建。
3. 得到真实 `threadId` 后执行 `register-successor --owner <旧ID> --successor <新ID> --token <token>`。若只有 `clientThreadId`，等待设置完成并取得真实 ID，不能将 client ID 用于注册、发消息或等待 API。一个 token 只登记一个接任者。
4. 按已授权范围向接任聊天发送登记和验包消息。接任者核实项目可访问、原始授权、state、冻结规格、证据、运行清单与下一步；缺失项列未知并补查，不能凭摘要宣布完成。语义验包前后核对清单哈希未变，通过后在其真实会话执行 `acknowledge-handoff --successor <新ID> --token <token> --manifest-sha256 <实际审查清单的小写SHA256>`；该命令在事务内匹配当前版本并再次验证冻结文件，不赋予调度权。清单已刷新或验包未通过则重读当前包并重新审查，不能用旧确认继续。
5. 旧主帅用 `wait_threads` 跟踪真实 ID、hostId 与 cursor，单次等待不超过 60 秒，不重复轮询不变状态。读取实际 control 确认已 ack，调用 `activate-successor --owner <旧ID> --successor <新ID> --token <token>`，原子转移 owner 并增加 epoch。接任激活未确认时不启新任务。
6. 旧主帅按授权向接任者发送激活消息。接任者必须重新 `assert-owner --owner <新ID>`，检查预算、闸门与 live run 后才调度。旧主帅已失去所有权，结束调度。激活消息发送失败时保留真实新 owner，新主帅读 control 恢复；不能把权限再偷偷交回旧主帅。
7. 宿主要求的创建聊天引用应如实展示；例如返回真实 threadId 时输出 `::created-thread{threadId="真实ID"}`，排队创建时用真实 clientThreadId。不要造 ID 或隐瞒创建结果。

所有权工具只保护 cooperative 调度，不是账户权限系统。实际 caller ID 必须从宿主取得，不能伪造参数。事务锁阻止并发覆盖；遇 `.control.lock` 先核对锁内进程与实际运行，不能盲删。崩溃恢复时确认无活跃事务且备份控制文件，才移除确实遗留的锁。阶段文件有变动时验包拒绝，应修复对应包而非绕过校验。

## 不可自动交接时

工具缺失、项目访问受限、用户授权不能核验或创建状态不明时，保留冻结交接包、说明具体原因，给同样自包含的手动启动语。用户手动开启新聊天后仍按登记、验包、激活协议移交，不能让新主帅 `init` 覆盖旧 owner。

缺证据/校验不通过时旧 owner 保留，派发保持冻结。需要修订包时保留旧清单，补齐事实后另存新版，由旧主帅执行 `refresh-handoff --owner <旧ID> --token <原token> --manifest <新清单绝对路径> --note <修订原因>`。该动作保留同一接任者，清除旧 ack；按已授权范围通知接任者核验新包并再次 ack，不能因一次验包失败重复创建聊天。达到轮换条件时不得以“读数现在降了”撤销轮换、无限压缩或在旧会话展开新的研究阶段。
